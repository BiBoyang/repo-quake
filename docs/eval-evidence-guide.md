# 从故障注入到可信结论：Eval 证据链实践指南

这套方法回答的不是“测试绿了吗”，而是：**我们凭什么相信自己看到的结果？**

一次评测可能同时发生四件事：目标产品确实出错、实验夹具没有按设想工作、判分器误读了结果、发布系统让写入状态变得不确定。把它们混成一个 pass/fail，就会得到很漂亮但不可信的数字。

## 一条主线：结论必须穿过四道检查

可以把可信结论拆成四个必要环节：

1. **故障按预期送达**：目标遇到的确实是我们声明的故障。
2. **独立 witness 在场**：证据不只来自被测系统自己的“我成功了”。
3. **判分遵守冻结合同**：不能看到结果后再改变判定标准。
4. **公开状态经过读回**：issue、PR、远端分支的实际内容与本地一致。

任何一环断裂，都应该降低结论等级，而不是继续累加“发现”。

## 三本账：产品、夹具、判分器

| 账本 | 典型情况 | 应该怎么处理 |
| --- | --- | --- |
| 产品故障 | 预期故障已送达，产品行为违反合同 | 最小化复现，形成 finding |
| 夹具故障 | 浏览器缺失、路由错误、种子错误、故障构造错误 | 记 `invalid setup`，修复后另开有独立预算的实验 |
| 判分器故障 | grader 增加合同外条件，或误读原始证据 | 保留初判输出，另写 adjudication，不靠重跑产品解决 |

### 案例：真实点击不等于目标故障已送达

本轮原想验证“动作已经点击，随后返回 `ACTION_MAY_HAVE_COMMITTED`”。夹具却少传了 `EngineError` 的必需参数，实际产生的是 `TypeError`。随后出现两次保存请求。

如果把“有两次请求”直接归因于产品，就会得到一个错误 issue。正确结论是：目标错误类型没有送达，重复请求是夹具诱导行为，属于 `invalid setup`。

所以 delivery proof 必须同时记录：

- 错误类型、code 和必要参数；
- 注入发生在哪个动作、哪个时机、第几次；
- 副作用发生之前，目标语义是否真的到达 runner。

**看到伤口，不等于看到了实验卡上写的那种伤口。**

### 案例：grader 比实验合同更严格

修正后的 replay 先完成一个动作，再把不确定动作交给 executor。合同要求 `reason=action-uncertain`，实际也完全正确。grader 却额外要求 `mode=missed`，而部分 replay 后交接的合同语义是 `agent-concluded`。

这不是产品失败，也不需要再跑一次产品。正确处理是：

- 原始 `matrix.json` 保留错误初判；
- 另写 `adjudication.json`，指出错误断言和正确合同；
- 在 deviation log 中公开修正，不回改预注册文件。

## 业务成功与报告完整是两件事

至少三种返回路径值得分别验证：

| 路径 | 例子 | 要观察什么 |
| --- | --- | --- |
| 正常成功 | 返回 `{bytes: 128}` | 是否得到 `saved` |
| 哨兵值 | 返回 `undefined` | 是否按合同得到 `not-written` |
| 异常抛出 | `throw EACCES` | 异常是否被控制，报告是否仍保留结果 |

本轮最有价值的发现正是第三种情况：业务只执行一次、测试通过、异常被吞掉，但报告里的 `step.cache.write` 没有生成。

因此这些字段必须独立观察，不能互相冲销：

- `detected`：系统是否发现异常；
- `reported`：用户能否看到正确的状态；
- `contained`：是否阻止重复或扩散；
- `recovered`：是否恢复正确状态；
- `reverified`：恢复后是否由独立证据再次确认。

“没有重复扣费”不能证明“用户知道缓存没有写入”。

### 字段缺失先问三个问题

1. 合同允许此时缺省吗？如果是，缺失可能完全正确。
2. 是 harness 把判分必需材料弄丢了吗？如果是，属于 `invalid setup` 或 ungraded。
3. 合同要求结果，而产品没有生成吗？这时缺失本身才是候选缺陷。

不能仅凭“字段不存在”就判断健康或失败。

## witness 应该证明什么

一个完整证据链通常包含：

- **送达证据**：错误 code、协议事件、当前路由、注入次数；
- **动作证据**：真实执行了哪些操作，顺序是否一致；
- **副作用证据**：独立服务器账本、文件变化、外部状态；
- **呈现证据**：最终 DOM、报告字段、用户可见警告；
- **恢复证据**：后续健康操作是否仍然正常；
- **发布证据**：远端 issue 正文、PR head、分支 SHA、权限结果。

同一 finding 在完整产品和最小函数上各复现一次，是两层证据，不是两个 bug。

## 发布也是不确定提交

网络超时并不区分“服务器没收到”与“已经写入但响应丢失”。因此公开发布也要遵守不确定提交原则：

1. 使用唯一标题或其他去重键查询；
2. 确认不存在后再提交，重试必须有上限；
3. 写后读回标题、正文、标签和当前 head；
4. 权限不足时记录边界，不换个接口绕过；
5. push 后独立核对远端 SHA，不能只看终端显示成功。

issue 正文中的 repro 也要作为交付物验收：**提取实际要发布的代码块，在独立环境执行一次。** 内部 harness 能跑，不代表维护者复制后也能跑。

## 对外分享时怎样讲这次实践

这次从 e2e 的 cache 行为开始，最后形成一个可提交的修复。可以按下面顺序讲：

1. 用 cached / no-cache / 参数变化建立语义对照，而不是只测缓存命中率。
2. 在缓存写失败处区分业务副作用、异常控制和报告结果，发现 `not-written` 缺失。
3. 用完整 runner 和最小函数两层复现，并检查 main 源码；明确“npm 运行结果”和“main 源码观察”不是一回事。
4. 用独立 issue 先建立上游 loop，再公开证据，避免证据链接指向尚未公开的材料。
5. PR 先证明新测试在 main 失败，再证明分支修复，随后跑完整检查、真实 runner 和 A/B。
6. 对权限限制保持透明：Mintlify 审批和 Ready 标签需要维护者，不把它们写成已完成。

## 可以带走的检查清单

### 实验前

- 写清故障类型、送达方式、独立 witness 和停止条件。
- 冻结 rubric、预算、invalid rules，并预检故障构造。
- 设计正常、哨兵值、异常抛出以及后续健康对照。

### 判分时

- 先问产品、夹具还是 grader，再决定是否形成 finding。
- 字段缺失先查合同，不把缺省、丢失和未生成混为一谈。
- 保留原始输出；修正实验与 adjudication 走不同路径。

### 发布与归档

- issue 自包含，公开代码块已经独立执行。
- 公开写入先去重、再读回；权限错误不绕过。
- 用 `audit_artifacts.py` 检查 symlink、运行时目录和常见凭据，不为 lint 改写原始日志。

```bash
python3 skills/repo-quake/scripts/audit_artifacts.py <experiment-directory>
```

更细的规则见 `skills/repo-quake/references/failure-attribution.md`、`measurement.md` 和 `reporting.md`。
